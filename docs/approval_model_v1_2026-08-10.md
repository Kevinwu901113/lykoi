# 审批模型 v1 · 对话式 + 一次授权长期有效 · 2026-08-10

- **地位**: Kevin 2026-08-10 补充定案，是具身重设计 v1 §1.2 三层门的细化。
- **一句话**: 除高危动作每次都问外，其余要么不问，要么**问一次就够**——但授权必须锚在
  正确的**范围键**上，否则"问一次"会变成"开一次口子全都过"。

---

## 1. 三层门 + 授权持久化

| 层 | 动作类 | 首次 | 之后 | 依据 |
|---|---|---|---|---|
| **免询** | 只读 / 无副作用 / 无外发 | 直接执行 | 直接执行 | policy_core 无副作用类 |
| **一次授权**（ask-once） | 有副作用但常规：`messenger.send` 给某人、访问某域名、写某路径 | **她用语言问，Kevin 用语言答** | **同范围内自动放行** | 批准落成 `approval_rules.json` 的常设规则（作用域受限） |
| **硬门**（ask-every-time） | `terminal.exec` 等高危 + 所有者管理类 | 每次都问 | **每次都问**，永不提升 | `policy_core.HARD_ASK_TYPES`（root-only，她改不了） |

**架构早已为此留位**：`policy_core.hard_decision()` 的既有注释写明，强制审批
"downgrades any live allow —— 无限制 shell 可以逐条批准，**但永远不能被提升为常设自动执行**"。
反过来即：**不在硬门里的动作，活规则里的 allow 本来就可以是常设的**。
本设计只是把这条路接通，不发明新机制。白皮书 22.3「自适应审批」即此。

## 2. 授权范围键（本设计最关键的一条）

**批准一次，到底记住了什么？** 范围过宽 = 安全事故；过窄 = 反复打扰。

| 动作 | 范围键 | 一次批准的含义 | 反例（禁止） |
|---|---|---|---|
| `messenger.send` | **收件人身份**（`identity_bindings` 里的 user_id / 未绑定者的 channel_key） | "以后可以给**这个人**发消息" | "以后可以给任何人发" |
| `browser.navigate` / `research_browser.open` | **注册域名**（eTLD+1） | "以后可以访问**这个域名**" | "以后可以访问任何网站" |
| 文件写类 | **路径前缀**（realpath 后判定，沿用 `path_guard`） | "以后可以写**这个目录下**" | "以后可以写任何地方" |
| `terminal.exec` | —— | **不可授权**（硬门） | —— |

**范围键的三条纪律**：
1. **默认最窄**：模棱两可时取更窄的键（沿用"拿不准往严"）。
2. **只能收紧不能放宽**：活规则永远不能超出 `policy_core` 的边界（既有铁律）。
3. **可撤销**：每条常设授权可被 Kevin 单条撤销，撤销即时生效。

## 3. 一次授权的生命周期

```
她想做某事（带具体范围键）
  → 查常设授权：命中且未过期 → 直接执行（只记审计，不打扰）
  → 未命中 → 她用语言问 Kevin（说清做什么、为什么、范围多大）
      → Kevin 自然语言回答
      → 解释器判定：批准 / 拒绝 / 有条件 / 不明确
          · 不明确 且 高危 → 追问到无歧义
          · 不明确 且 常规 → 追问一次；仍不明确 → 按拒绝处理（不猜）
      → 批准 → 写入常设授权（含范围键、授权时刻、Kevin 的原话）
      → 拒绝 → 记录，且**同范围短期内不再问**（防骚扰；但不是永久拒绝）
```

**必须落审计的四元组**（沿用具身设计 v1）：问题原文、回答原文、解释结果、风险级。
再加两项：**范围键**与**是否产生了常设授权**——事后可复盘"我当时到底授权了多大范围"。

## 4. 与既有基础设施的接线

- **常设授权的存放**：`approval_rules.json`（既有活规则文件，policy_core 已保证它只能收紧）。
  范围键作为规则条目的一个字段；不新建存储。
- **偏好证据**：`permission_evidence` / `permission_learning`（P2 之前就存在的表）——
  Kevin 的每次批准/拒绝本就是高价值偏好信号，接上后这条链闭环。
- **解释器**：属 S2 工单，挂在 messenger 入站处理与 policy_core 之间。

## 5. 未决（留给 S2 实现期）

1. 常设授权要不要有**有效期**（如 90 天后重新确认）？倾向：不设默认过期，但提供
   "定期回顾清单"让 Kevin 一眼看到自己授权过什么。
2. "有条件批准"（例如"可以，但别提我家地址"）如何编码进规则？倾向：首版把条件原文
   随规则存下并注入她的上下文，不做机器可执行的条件判定。
3. 撤销的入口形态（对话里说"以后别再给他发了"是否足够？——倾向：是，但需二次确认）。
