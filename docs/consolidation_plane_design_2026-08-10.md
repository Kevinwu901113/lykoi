- **地位**: 框架已由 Kevin 认可（"可以"）；本文件把框架落到**判据**与**咬合**两层，
  这两层待审。兑现白皮书 13 章（离线巩固/做梦）与 14 章（学习的分层定义）。
- **缘起**: 闲置能力清点（`reports/idle-capabilities-survey_2026-08-10.md`）发现
  她 55 天没形成新洞察，而根因不是四个 bug，是**巩固器官的产物面太窄**。

---

## 1. 现状：一个器官，只接了一条消化道

`mind/integrator.py` 是完整的巩固器官（每晚七步：消化经验 → LLM 结构化输出 →
四操作 → 关切取舍 → 叙事重写（连续性门）→ 念头清算 → 重置）。它很活跃：
510 个叙事版本、9 个关切在动、5923 条调节事件。

**但它只写叙事/关切/念头，不写 insights、procedures、策略。它甚至不读 autonomy_notes。**

结果：**她在"我是谁"上持续成长，在"我了解你"上停在 2026-06-15。**

## 2. 统一契约（四条消化道共用同一副骨架）

每条消化道必须声明这五样，缺一不可：

| 要素 | 说明 | 为什么必须统一 |
|---|---|---|
| **原料流 + 游标** | 从哪读、读到哪 | 防重复消化、可断点续跑 |
| **判据** | 什么值得晋升（见 §3） | 这是四条死链共同缺的那个东西 |
| **产物 + 血缘** | 结论 + 它由哪些原料得出 | 可回溯"她为什么这么认为"（白皮书可审计要求）。`note_insight_links`（P2-01 已建）泛化为通用血缘表 |
| **门** | 产物是否允许影响行为（见 §4） | 影子/放行机制**只造一套**，不让每个学习子系统各发明一个 |
| **预算** | 每周期消化上限 | 加新消化道不会让巩固周期失控 |

**双向性（架构硬要求）**：每条消化道**必须同时有晋升与撤销/修订路径**。
产物是长期存在的，只进不出必然腐烂——她会抱着两个月前的错误结论不放。
integrator 对经验已有"重释/修订"四操作，同一纪律必须套用到 insights / procedures / 规则。

## 3. 四条消化道与各自判据

### 道 A · 经验 → 叙事/关切（已有，原样保留）

判据即现有四操作（吸收/重释/修订/悬置）+ 叙事连续性门。**不动它**——它是唯一活着的，
本设计的目标是让另外三条达到同等成熟度，不是重写它。

### 道 B · 观察笔记 + 经验 → `insights`（关于你与世界的知识）【要修的核心】

**什么算一条 insight**（四条同时满足才晋升）：

1. **跨场合重复**：≥2 个**不同场合**观察到（同一次对话里说三遍算一次）；
2. **未被更近证据推翻**：与更新的原料不冲突；
3. **可操作**：它会改变她说话或行动的方式（不可操作的"事实"是噪音）；
4. **关于持久实体**：人、关系、项目、长期偏好——而非一次性事件。

**类别**沿用既有 6 条的分类（`preference` / `persona`），按需扩展。
**血缘**：每条 insight 必须链到 ≥2 条原料（否则不满足判据 1）。

**撤销路径（同等重要）**：新原料与既有 insight 冲突 → 标 `contested` →
下一周期冲突仍在 → 修订或撤回，并**保留历史**（她曾经这么认为过，这是身份连续性的一部分）。

### 道 C · 执行收据 → `procedures.reliability`（她的能力自知）

**判据分两级，优先客观**：

1. **有客观信号时**（exit code、断言、Gateway 合同的 `success_criteria`）→ 直接判定，
   `evidence_status=objective`；
2. **无客观信号时** → LLM 事后判断，`evidence_status=judged`，且**权重低于客观证据**。

`reliability` 只能由此更新，**她不能自报可靠性**（单写者原则）。

**注意依赖**：真正的客观判据来自 Gateway 任务合同的 `success_criteria`。
Gateway 落地前，道 C 只能跑"事后判断"级别——**这是可接受的起步，但要在产物上标清楚**。

### 道 D · 决策事实 → 策略规则 / 显著性放行（她的行为边界）

**权限学习判据**：同一 `(action_type, 范围键)` 上 Kevin 连续 ≥N 次批准且零拒绝
→ **生成一条"建议提升为常设授权"**。范围键定义见 `approval_model_v1`。

**显著性放行判据**：沿用 2026-07-08 已预注册的门（影子 ≥14 天 + 全局吸收率 ≥5%）。
注意：吸收率依赖道 B 修好——**两者互相锁死**（bandit 的 reward 锚是 nightly 的
`accepted_op`，晋升不工作就永远只有正证据，实测 posterior 的 beta 全是 1.0 未动过）。
**道 B 修好后此门才有意义，因此道 D 的显著性部分排在道 B 之后。**

## 4. 门的强度随"产物影响什么"递增（本设计的核心安全规则）

| 道 | 产物影响 | 门 |
|---|---|---|
| A | 她的叙事与关切 | 连续性门（已有），自动 |
| B | 她的知识 | 影子期 → 自动放行 |
| C | 她的能力自评 | 影子期 → 自动放行 |
| **D** | **她自己的权限边界** | **必须所有者批准，永不自动** |

**道 D 的铁律**：她可以**观察到**"Kevin 这类事总是批准"，可以**建议**把它变成常设授权，
但**绝不能自己写进 `approval_rules.json`**。这与 `policy_core` 现有设计一脉相承
（她不能编辑自己的能力白名单）。建议 → 问你 → 你批 → 才生效。

**这条规则同时解决了一个实现问题**：道 D 的"问"走哪条路？——**走 messenger**。
她在 Telegram 上问你"这类事我以后能不能不用每次问"，你回一句话，
解释器判定后写规则。**巩固平面与社交器官在此咬合**。

## 5. 与阶段 2 既定设计的咬合

| 阶段 2 组件 | 在巩固平面里的角色 |
|---|---|
| `note_insight_links`（P2-01 已建） | **通用血缘表的第一块**，泛化为 `(道, 产物类型, 产物 id, 原料类型, 原料 id)` |
| `procedures` 表（P2-01 已建） | 道 C 的产物容器（`reliability` 字段等着被喂） |
| Delegation Gateway 的**执行收据** | 道 C 的**客观判据来源**（`success_criteria` + `required_evidence`） |
| `approval_model_v1` 的 **ask-once 常设授权** | 道 D 的**产物形态**（`permission_decision_facts.scope` 字段已预留 episodic/standing 之分） |
| `messenger` 器官 | 道 D 的**所有者门通道**（她在 Telegram 上问，你用语言答） |
| `memory_scopes`（P2-01 已建） | 道 B 产物的语境标注（哪条 insight 属于哪个语境、可否在群聊引用） |

**结论：巩固平面不是新增的第五块，而是把阶段 2 已经铺好的四块接通的那根线。**
不接这根线，P2-01 建的 procedures/血缘表就会变成下一批"建好了没用上"。

而不是等你翻数据库发现。这是需求分析 D5 的最小落地，独立于巩固平面。
