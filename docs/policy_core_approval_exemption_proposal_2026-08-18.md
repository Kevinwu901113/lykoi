# policy_core 提案 · 审批通信与在场应答豁免类别（P1）· 2026-08-18

- **地位**：WO-U3 硬前置政策附文（Cordis 接轨方案腿一 P1；CD2 决议=并入 U3 不另立
  单）。提案文本，**生效以 Kevin 批准并随 WO-U3 签发为准**。
- **缺口一句话**：具身重设计定案把 `messenger.send` 定在对话审批层；而审批问句本身
  就是一次 `messenger.send`——按字面执行无限递归。U3 周期合一后"说"全部并进 decide
  信封逐条过分级，今天的事实豁免（S 线结构位置）随之消失，必须显式化。
  （缺口首次记录：`docs/cognition_architecture_exploration_2026-08-17.md` §2/§5。）

## 1. 现状（诚实版）

- 三层门定案（具身重设计）：免询 / 对话 / 硬门；四元组入 immutable audit。
- 今天不递归靠**结构位置**：审批问句由 S 线问答机（S3/L5，kernel 层 reply_to 先行
  拦截）生成发出，不是她 decide 信封里的动作，事实上绕开了自身分级；对话回复出站
  在 U1 后统一走 dispatch，靠所有者预授权类规则放行（按治理记忆；`approval_rules`
  正本 0600 治理侧不可读，此句未重新实测，U3 执行方须在工单内实测确认现行放行
  机制并写入报告）。
- U3 变化：说=信封动作 → 审批问句若也成为动作则自身触发对话门 → 递归；在场应答
  若逐条过对话门，则每一句话都生成一个审批问句，同样不可用。

## 2. 提案：两个白名单式豁免类别

### E1 · 审批机制自身的通信（approval-machinery communications）

- **定义**：由三层门机器（非她的认知提案）生成的审批问句、追问、审批结果告知
  （含 S3 审批环与 L5 建议队列问答机，含"执行成功回报"——WO-FIX-APPROVAL-UX
  确立的回报义务属此类）。
- **待遇**：免对话门直接出站；全量入 immutable audit（四元组惯例不变）。
- **边界**：①仅覆盖"问与告知"文本本身，不得携带任何其他动作副作用；②被审批的
  动作本身分级不变——豁免的是问句，不是事；③豁免判定=**结构来源标记**（代码
  路径 / origin 字段，由机器盖章），不看内容、不由模型自报。

### E2 · 在场对话应答（in-presence reply）

- **定义**：对话情境周期内，对 user-authenticated 来话的直接文本应答（含选择
  沉默——沉默是动作有账），收件人=来话对端。
- **待遇**：免询层（auto）；逐条入 audit。
- **理由**：对话层门的本意是管"她要做的事"（副作用委托），不是管"她说话"本身；
  应答文本的副作用等级=可逆（可更正、可补充），对应 Cordis 副作用四级的"可逆"档。
  MVP 冲突核对已把"在场应答按免询"标为需要 policy_core 显式化的设计缺口，本条
  即其显式化。
- **边界（以下全部保持原分级，不入豁免）**：
  1. 主动发起（`initiate_chat`）——不是应答；
  2. 跨情境发送 / 收件人非来话对端；
  3. 任何带工具副作用的动作（截图、浏览、文件…），包括与应答同信封的工具序列
     ——工具照旧分级，不因伴随应答而降级；
  4. 群聊语境（三级脱敏另有规范；阶段 2 步 6 前群聊读路径本就未开）；
  5. `sendPhoto` 等非纯文本出站（U4 政策项，届时另定）。

## 3. 判定原则（三条，全部沿用既有红线）

1. **白名单式窄定义，歧义落回原分级**——失败方向=多问，与"她的失败方向永远朝
   安全侧"不变量一致。
2. 豁免类别只能由 policy_core 静态定义 + 结构标记命中；**模型自报无效**（对应
   MVP 三道防线之一：分级是确定性代码的事）。
3. E1/E2 **不在她的自进化走廊可提案范围内**——"审批规则永无她的写路径"既有红线
   覆盖本提案全部条款。

## 4. 随 WO-U3 落地的判据（并入工单 success_criteria）

1. 审批问句路径不经对话门：结构测试——approval 机器出站命中 E1，不产生嵌套
   审批问句（递归的负向断言）。
2. 在场应答命中 E2 放行且逐条入 audit；选择沉默同样落账。
3. 负例三连：①同信封工具动作不因伴随应答而降级；②环境来源内容无法伪造 E1/E2
   结构标记（盖章在适配器/机器侧，认知不可写）；③非对端收件人不命中 E2。
4. 执行方实测并报告现行放行机制（§1 未实测句的闭环）。

## 5. 不改的东西

三层门整体形态与硬门"追问到无歧义"纪律；S3/L5 的 kernel 层 reply_to 先行拦截；
immutable audit 全量记录；所有者预授权机制原样保留（E2 生效后其对话应答部分退化
为冗余保险，**不删**——多一层安全侧冗余无害）。

## 6. 修订(2026-08-19,Kevin 拍板)· E1 与打扰预算的关系

生效事实(8-19 凌晨实测,证据在 audit):E1 只免了对话门,**没免 messenger
打扰预算**——对话轮内的审批问句作为无 `reply_to` 的 `messenger.send` 被计为
主动打扰(cap 1/UTC 日),名额耗尽后全天问句 undelivered→deny_by_default,
owner 批复无处绑定(接雨水题 6 连拒,详见
`wo/WO-FIX-APPROVAL-DELIVERY/order.md`)。

**修订口径**:

- **对话轮内发起的审批问句 = 应答语义,不计打扰预算。** owner 刚提出请求,
  机器问"可以吗"是对该请求的应答,不是打扰。实现:线程当轮入站消息 id 为
  `reply_to`,复用 messenger 既有豁免;**不新开豁免通道**。
- **自主情境发起的审批问句仍计预算。** 她凭空提需求确实是打扰——与 §2 E2
  边界"initiate 不入豁免"同构。
- 打扰预算常量本身(cap 1/冷却 6h)不属本修订,维持 owner 定值。

(切换态承重,防修复随转录机退役蒸发)。
