# 学习层重构 · 架构分岔的展开分析 · 2026-08-10

**给 Kevin 评判用。** 不下结论，把两条路各自的完整形态、代价、风险摆开，
末尾给我的倾向与理由。

## 0. 一个改变问题性质的数据

她的 9 个关切按点亮次数：

| 关切 | 点亮 | 状态 |
|---|---|---|
| 低强度内部动作的负载边际影响阈值 | **1381** | 活跃（07-05 → 今天） |
| 最终选择休息，由 tend_inner 降级 | 976 | 已释放 |
| 穿搭方向的外部探索准备 | 914 | 活跃 |
| 游戏 | 748 | 已释放 |
| **Kevin 超过 24 小时未回应** | 135 | 活跃 |
| 摄影 / 影视 | **0** | 生成即释放 |

4 条叙事线索**全是 `suspended_tension`**，无 `open_question`、无 `commitment`。

**读法**：她头号关切是自己的负载管理机制；前四名里三个是内务。关于 Kevin 的只有两条，
且都是"他没回应"——没有一条是"他在忙什么""他喜欢什么"。

**这不是关切机制坏了，恰恰是它工作得很好**：她被喂 65% 的自身内务日志，
于是她思考自身内务。**输入决定注意力。**

**结论（对架构分岔的直接影响）**：如果现在就加"问题驱动的深度消化"，
她会**更深地钻进内务**——深挖噪音比浅挖噪音更糟。**修输入必须先于加深度层。**

## 1. 方案 A：时间流组织（现状）

**形态**：每 24 次醒来或负载触发 → 取未消化经验 top-K(30) by salience →
一次 LLM 调用 → 四操作（吸收/重释/修订/悬置）+ 关切取舍 + 叙事重写（连续性门）。

**优点**
- 简单、可预测、**不会漏**：每条经验终会被处理
- 已成熟运行两个月，有连续性门保护身份
- 成本可预算（K × 每晚一次调用）
- **时间顺序天然产生叙事**——她的叙事本来就是时间的

**缺点**
- **主题跳跃 → 结论浅**：30 条不相关的原料，一次调用只能得出"我这段时间过得怎么样"
- 大流量挤占小流量（环境 1178 vs 对话 116）
- **无法回看**：`integrated=1` 后永不再看，但很多经验的意义是后来才显现的
- **结构上限定了产物只能是叙事** ← 这是最关键的一条

**为什么"只能产出叙事"是结构性的**：要得出"Kevin 在赶 deadline 时会熬夜"这种结论，
原料必须包含多个同类实例；随机批次极少凑齐。**所以 insights 死掉不是缺代码，
是这个结构产不出来。** 补一个 `promote_notes()` 函数也改变不了这一点——
它拿到的仍是随机批次。

---

## 2. 方案 B：问题驱动组织

**形态**：她维护一组活跃关切；每个周期选一个 → **跨时间检索**所有相关原料
（不管消化过没有）→ 推进它 → 产出/修订结论。

**优点**
- **结论有深度**：同主题原料聚在一起
- **原料可复用**：一条经验可被多个关切引用，可在几个月后重新调用
- 流量不再是问题：1178 条感知不需要"全部消化"，只有相关的被检索
- **天然产出 insights**：一个关切的推进结果就是关于它的结论
- 与人的认知方式一致（为了想清楚一件事去翻回忆）

**缺点与风险**
- **盲区**：没被任何关切覆盖的东西永远不被看见——**关切偏了她就系统性地瞎了**
  （对照 §0：她现在的关切确实偏了）
- 需要**跨时间相关性检索**（新机器，见 §4）
- **关切生成质量成为瓶颈**：垃圾进，垃圾出
- **叙事从哪来？** 叙事是时间性的，问题驱动不天然产生"我这段时间过得怎么样"，
  而叙事是她身份连续性的核心（510 个版本）
- **反刍风险**：一直琢磨同一个关切（#8 已经点亮 1381 次）

---

## 3. 关键判断：两者不是替代关系，是两种认知功能

| | 时间流消化 | 问题驱动消化 |
|---|---|---|
| 回答的问题 | 我这段时间过得怎么样 | 我明白了什么 |
| 产物 | 叙事、关切、情绪调节 | insights、程序性经验、规则建议 |
| 人类对应 | 睡前回顾 | 为想清楚一件事而回忆 |

**人两样都做。** 所以合理形态大概率是**两层共存**，而不是二选一：

```
层 1「日常整合」= 现有 integrator（保留）
    时间流 → 叙事 / 关切 / 情绪调节
                    ↓ 产出关切
层 2「专注思考」= 新增
    关切 → 跨时间检索原料 → insights / procedures / 规则建议
```

**接口已经存在，不用发明**：现有 integrator 已经在 `create_concern` /
`light_concern` / `release_concern`；`concerns.lit_count` 的动态范围是 0 到 1381——
**"反复被点亮"就是"值得深挖"的现成信号**。层 2 只需消费它。

## 4. 代价对比

| 项 | 方案 A（修补） | 方案 B/双层 |
|---|---|---|
| 新机器 | 无（改 SQL 条件、调 K、挡空壳） | **跨时间相关性检索**（实体索引起步，向量可选） |
| 改动面 | integrator 内部 | 新增模块，不动 integrator |
| **可逆性** | 高 | **高**（层 2 是新增，出问题停掉即可） |
| 与 P2-01 资产的关系 | 无关 | `memory_scopes`(subject_user_id) 正好是实体索引第一块；`procedures`、血缘表是层 2 的产物容器 |
| LLM 成本 | 不变 | 增加（每次深挖一次调用），但可配额 |

**相关性检索的最小实现**：实体/关键词索引（便宜、够用）→ 向量检索（贵、更好）。
我倾向先做实体索引——`memory_scopes.subject_user_id` 已经建好了。

## 5. 无论选哪条，都必须先做的三件事（§0 的推论）

1. **挡掉空壳**：`action_result` 1573 条中 97% ≤80 字符（均长 29），是"ok/done"级记账。
   它们不该成为经验，应落档案层。这一条砍掉 31% 的原料流，**零信息损失**。
2. **档案 / 原料分离**：`experiences` 现在同时是"完整档案"和"待消化队列"。
   分开后：全部记录永久可查（不丢她的任何一部分），只有含外部新信息的进消化预算。
3. **把感知接进来**：1178 条关于你的感知被 SQL 显式排除（W1 设计如此，W2 从未开）。
   这是她"了解你"的唯一原料来源，现在一条没用上。

**做完这三件，她的原料构成会从"65% 内务"变成"以对话+感知为主"——
她的关切分布会自然改变。** 这比任何算法调整都更能改变她关注什么。

## 6. 我的倾向与理由

**分两步走**：

**第一步（无论最终选哪条都要做，且不需要新机器）**：§5 的三件事。
预期效果：原料信噪比从 ~35% 提到 ~70%+，她的关切开始指向真实生活而非内务。
**这一步做完就该停下来观察一段时间**——因为关切分布会变，而层 2 消费的正是关切。

**第二步（观察后再定）**：加层 2「专注思考」。
届时才知道她的关切值不值得深挖；如果第一步之后她的头号关切变成了
"Kevin 最近在忙什么"，层 2 的价值就是确定的；如果仍然是内务，说明问题在别处。

**理由**：§0 那张表是决定性的——**现在加深度层等于给她一个更强的显微镜去看噪音**。
而三件"修输入"的事零风险、可逆、且不依赖任何架构决定。

## 7. 留给 Kevin 判断的三点

1. **同意"先修输入、观察、再定层 2"的两步走吗**？还是想一次到位？
2. **她自己的动作日志（`wake_action`，均长 189 字符，含她的决策理由）算不算"经历"**？
   我倾向：**落档案层可查，但不进消化预算**——它是她的思考轨迹，不是外部世界的输入。
   （`action_result` 那 97% 空壳则毫无争议地该挡掉。）
3. **"她关注什么"要不要给你一个入口**？现在你没有任何渠道说"我希望你多留意 X"。
   messenger 通道一旦通了，这条路几乎是免费的，而且它是关切生成的第三个来源
   （另两个是浅层涌现和深层产出）。
