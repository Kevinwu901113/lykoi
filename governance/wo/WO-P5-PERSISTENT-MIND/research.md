# Lykoi 下一阶段研究与架构方案

**我的结论是：应该重构认知主干，但不应该推倒所有已经验证的基础设施。**

下一阶段不再以“增加一个功能模块”为中心，也不把 P5 简单定义成 Forge 或新客户端。我建议把它正式调整为：

> **P5 — Persistent Mind：让思考成为持续过程，让任务、交互与学习成为这个过程的延伸。**

目标不是让模型不停生成文字，而是：

> **一次对话结束、一次模型调用结束、一个任务结束，都不意味着这个个体的思考已经结束。**

本次研究区分三种依据：你提供的报告是 **9 月 4 日的历史架构快照**，不能作为 P0–P4 完成后的当前事实；我重新核对的 GitHub 基线是 **`main@a49e01b`**；下面的新架构则是基于论文和工程机制提出的设计，不是仓库已经实现的功能。当前线上实际部署版本及 Telegram 故障后台证据，仍未得到验证。

---

## 一、相关研究真正支持什么

与这个目标最相关的，不是某一个“万能 Agent 框架”，而是几条可以组合的研究路线。

| 研究方向           | 代表工作                      | 可以借鉴什么                                             | 不应该直接照搬什么                                                                |
| -------------- | ------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| **认知架构**       | CoALA                     | 区分工作记忆、长期记忆，以及检索、推理、学习和外部行动。“想”可以是内部状态变化，不必立即调用工具。 | 不需要把每一种认知活动都拆成独立 Agent。([arXiv][1])                                      |
| **持续经历与反思**    | Generative Agents         | 从经历中检索相关内容，形成带来源的高层理解，再影响后续行为。                     | 模拟小镇中的可信行为，不等于证明真实产品中的长期个体性，更不等于证明意识。([arXiv][2])                        |
| **行动结果反馈**     | ReAct、Reflexion           | 用真实观察修正行动；把失败反馈概括成可供后续使用的语言经验，无需每次更新模型权重。          | 不必照搬 Actor/Evaluator/Reflector 三套常驻组件，也不能把现实任务当作可以随意重置的实验环境。([arXiv][3]) |
| **空闲时思考与准备**   | Sleep-time Compute、ProAct | 在用户再次提问之前，利用已有上下文进行准备、查证和组织材料。                     | 空闲计算不是越多越好；收益取决于未来需求是否可预测，错误准备也可能浪费资源或干扰回答。([arXiv][4])                  |
| **跨任务经验与技能凝练** | ExpeL、ACE                 | 比较真实成功与失败，提炼跨任务方法；采用局部更新，保留有价值的细节与例外。              | 不把整套经验反复重写成越来越空泛的总结，也不必引入评分、投票和策展流水线。([arXiv][5])                        |
| **学习用户偏好**     | PRELUDE / CIPHER          | 从用户修改与反馈中学习自然语言形式、具有情境的偏好，而不是只有静态标签。               | 论文主要使用模拟用户；其中的“未修改”信号，不能直接等同于真实聊天里的“没回复”。([arXiv][6])                    |
| **主动行为评测**     | ProEvent、LongMemEval      | 检查何时不应行动、需求如何变化、旧信息如何被更新，以及多会话中的一致性。               | 不能把主动消息数量、记忆条数当成能力指标。([arXiv][7])                                        |
| **可靠长期执行**     | Temporal、Orleans          | 持久等待、消息交付、独立执行上下文，以及串行状态更新与并发工作的分离。                | 当前不需要接入完整分布式工作流平台，也不需要自己重造一个。([Temporal 文件檔案][8])                        |

其中两条限制尤其重要。

**第一，反思不自动等于进步。** Reflexion 本身就指出，效果依赖反馈质量和错误归因；另有研究发现，无外部反馈的自我纠错在一些推理任务上会使结果变差。这不代表今天的模型都不能自我纠错，而是提醒我们：不能把“多想一次”当成普遍有效的工程规则。([arXiv][9])

**第二，最新的主动性研究也没有证明“多主动就更好”。** 2026 年的 ProAct 明确把结果限定为封闭合成环境中的证据；ProEvent 则观察到被测模型容易在不需要时过度介入。我们应借鉴机制与测试方法，不把论文结果当成 Lykoi 的部署保证。([arXiv][10])

因此，我采用的总原则是：

> **让模型拥有思考、行动和反思的机会；让真实经历决定这些过程是否有价值，而不是由框架预先制造“成长”。**

## 二、先纠正我们此前讨论中的几个过度简化

重新核对代码后，我认为不能只把剩余工作理解成“补两座桥”。

### 1. 共享循环，不等于共享心智

当前 `runCognition()` 明确把提示词、状态写入和交付留给调用方。它统一了 `reason → act → observe` 的执行机制，但没有统一持续身份、关注点、工作记忆与跨事件的认知连续性。

P2 是有价值的基础，但不能因此说“同一个 Mind 已经成立”。

### 2. 当前的“想”仍受“做”的预算限制

Wake 在小时行动额度耗尽时，会直接退出，尚未进入认知；而 `contemplate`、`record_note` 等内部行为通常又会结束这一拍。也就是说，当前并非“想独立存在，做是可选输出”，而是思考仍被行动周期包住。

这比缺少一个 `task.create` 更根本。

### 3. Task 能持续执行，但没有完整接入持续心智

当前 Task 使用自己的任务协议与操作历史，完成后回写一条 Experience；它没有与 Conversation/Wake 相同的 `inner` 输出通道。Task cognition 还通过 `origin: interactive` 执行，这对用户交代的任务可以理解，但未来不能原样用于角色自己发起的任务。

因此，“Task 想到事情后自然留给未来 Mind”的链路，不能靠一句提示词假定已经存在。

### 4. 单一 Mind，不应该意味着一个全局锁

当前 Task Runtime 有单一 `#active/#running`，会串行推进任务认知。它允许外部 Runner 等待期间继续处理其他事情，但还不是我们讨论的完整并行工作模型。

**要统一的是身份、承诺与状态归属，不是强迫所有模型调用排成一条队。**

另外，当前源码仍留有按关键词判定人格忠实性、用旧新叙事四字符重叠判断连续性的规则。这说明 P0 清理并没有消灭所有语义防御；新认知主干不应把这些规则继承成永久规范。

## 三、我决定采用的总体结构

我建议保留 Cordis，但把整个运行时重排成下面的关系：

```text
用户消息 / 世界变化 / 任务结果 / 到期事项 / 空闲机会
                         │
                         ▼
                  持久事件收件箱
                         │
                         ▼
                    Mind Episode
                 一段可以续接的思考
                         │
         ┌───────────────┼────────────────┐
         ▼               ▼                ▼
     更新思考状态       表达与交流        发起或调整工作
         │               │                │
         │               ▼                ▼
         │            Channel        Task / Capability
         │                                │
         │                          Worker / Pi / 工具
         │                                │
         └───────── 真实观察与反馈 ◀────────┘
```

这不是要求新增十几个包。

实际上只需要确立三个核心职责：

**Mind 负责理解与选择。** 当前什么值得想，什么值得做，结果意味着什么，是否应该找用户。

**Work 负责把事情推进。** 执行、等待、恢复、取消、保存材料和结果。它可以进行任务内部的推理，但不独立管理另一套人格和关系。

**Surface 负责感知与表达。** 把消息送进来，把真实回应、进展和成果送出去，不另造一套业务状态。

Memory、Thought、Skill、用户理解，是这些过程使用和更新的数据，而不是四个需要互相开会的 Agent。

下面逐项展开七个主题。

# 主题一：Mind——让“想”真正成为一等过程

## 1. 思考必须有独立于任务的存在方式

Lykoi 应该能够：

> 对一个问题产生兴趣，比较几种理解，发现尚缺证据，暂时保留，然后在后来的信息出现时重新接续。

这整个过程可以没有外部工具，没有用户回应，也没有新 Task。

例如：

```text
问题：
几个日志分析方法是否共享同一种诊断结构？

当前进展：
共同部分是“证据—影响—复核”，
但不同系统对“影响”的判断依据不同。

尚未解决：
哪些差异只是实现细节，哪些不能被泛化掉？

下一步可能：
再遇到一个不同领域案例时比较；也可以现在读两个旧 Skill。
```

这才是值得持久化的 Thought。

它不是原始模型思维链，也不是每轮生成的“内心独白”，而是**下一次能够据此继续工作的思考状态**。

CoALA 对内部推理、检索与学习动作的区分，为这种设计提供了清楚的概念基础：内部活动本身可以更新工作记忆，不必每次都转成外部行动。([arXiv][1])

## 2. 一个 Thought 不应只有一句内容

最小结构建议包括：

```text
问题或主题
当前理解与进展
尚未解决的部分
相关证据/经历引用
关联任务或 Skill
当前状态
可选的再次考虑时机
```

不必强制每个 Thought 都有浮点显著性、紧迫度、情绪电荷或价值评分。

这些数字只有在真实检索或调度中证明有用时才增加。否则只是把自然语言意义转换成难以解释的假精度。

同时，**Concern 与 Thought 不必各自拥有一套复杂引擎**：Concern 可以是较长期在意的方向，Thought 是其中正在推进的问题。先区分含义，不急着为每个名词建立服务。

## 3. Mind 的持续性由三个东西组成

**状态持续**：未解决问题与已经获得的理解不会随请求结束消失。

**注意力续接**：下一次认知能找到相关旧问题，而不是只能看最新聊天。

**变化积累**：新的推理与观察会改变已有理解，而不是每天重新生成类似的感想。

Generative Agents 展示了“经历检索 → 带来源的高层反思 → 后续行为”的一种实现；MemGPT 则强调有限上下文和长期存储的分工。这支持我们把“个体的全部状态”与“这一次模型看到的工作集”分开。([arXiv][2])

因此：

> **Mind 不是一份永远增长的聊天历史，而是一组能够被选择、继续和更新的认知状态。**

## 4. 思考如何继续：允许连续片段，也允许暂停

我不会限定“没有新事件就绝对不能继续想”，那仍然过于被动。

一个认知片段结束后，模型可以选择继续推进当前问题，也可以保存进展、等待证据、约定以后再看，或者什么都不做。运行时只负责实际执行机会和计算预算。

这里应拆开三类限制：

| 限制   | 控制什么               |
| ---- | ------------------ |
| 认知预算 | 能投入多少模型计算          |
| 执行预算 | 能启动多少外部工作、占用多少执行资源 |
| 联系设置 | 什么时间、什么程度可以主动打扰用户  |

**不能因为浏览器行动次数用完了，就禁止她继续思考；也不能因为允许思考，就默认允许一直给用户发消息。**

空闲计算可以用于推导、比较、准备或查证，但不能为了证明“活着”而强制产出内容。Sleep-time Compute 的结果也表明，准备是否有收益依赖上下文与未来需求的关系，而不是单纯增加计算。([arXiv][4])

# 主题二：Thought → Intent → Action——区分想到、决定和做到

## 1. 保留这个区分，但不多造一个 Intent 平台

经典 BDI 架构区分信念、愿望与意图，其价值就在于：知道什么、希望什么、承诺做什么不是同一件事。Lykoi 可以借这个概念，但不需要引入 BDI 的规则语言或计划库。([AAAI][11])

对应到 Lykoi：

| 概念            | 含义         | 例子                    |
| ------------- | ---------- | --------------------- |
| Thought       | 正在理解的问题    | “这些方法是不是有共同结构？”       |
| Intent        | 已经选择要推进的目标 | “我要比较它们，保留共同原则和重要例外。” |
| Action / Task | 已实际发起的工作   | 读取 Skill，或创建一个研究任务    |

但我会修改此前“中间增加 Intent 层”的说法：

> **概念上需要 Intent，工程上不一定需要单独的 Intent 数据库。**

短动作的意图放在操作记录中；长期意图放在 Task 的目标、原因和来源中。不要同时维护 Intent、Plan、Task 三份近似状态。

## 2. 自主任务与用户委托必须同样自然，但来源不能混淆

Mind 应该有一个通用的任务创建入口，不再绕过 Conversation 的 follow-up 功能。

它既可以表示：

> “用户让我研究这个项目。”

也可以表示：

> “这个问题和我已有的关注有关，我决定继续研究。”

两者共享 Task 机制，但保存不同来源及关联 Thought。

这不是为了再增加权限体系，而是为了保证：

**她自己想做的事情，不会被错误记录为用户已经要求或授权的事情。**

## 3. 做链可以聪明，但不能变成另一个人格中心

之前说“Executor 要很笨”，需要收紧解释。

文件读写器可以很简单，但 Pi 这样的执行器必须会规划、调试和修正。否则所有细节都返回 Mind，会产生大量不必要的往返。

正确分工应当是：

> **Mind 决定总体目标、承诺与跨任务意义；Worker 在目标范围内自主解决具体问题。**

不是禁止 Worker 思考，而是不让 Worker 另管一份“我是谁、我和用户是什么关系、我接下来的人生目标”。

# 主题三：Ambient Mind ↔ Persistent Task——可靠回流，而不是偶然读到

## 1. 两种反馈循环必须同时存在

**任务内部循环**：

```text
读取文件 → 得到错误 → 修改方法 → 重新验证
```

这类局部观察由当前 Task/Worker 使用即可。

**全局心智循环**：

```text
研究发现原假设不成立
    → Mind 重新理解问题
    → 调整另一个任务、修正 Skill 或联系用户
```

这里要修正“所有结果都立即唤醒 Mind”的表述：

> **所有实际结果都应可追溯，但不是每条日志、每个 token、每次文件读取都值得启动全局认知。**

Task 的完成、失败、阻塞，以及影响其他事项的重要发现，应成为 Mind 事件。其余材料保留在任务上下文或 Artifact 中，必要时读取。

## 2. 事件必须先保存，再安排思考

不能只在任务完成后执行一次：

```ts
emit('task.completed')
```

然后希望 Mind 正好在线接住。

也不能因为处于冷却时间就把事件丢掉。

建议采用一个很小的**持久事件收件箱**：事件有稳定 ID、来源、关联对象和处理状态。Mind 忙、用户正在聊天或当前没有计算额度时，事件留在收件箱里，稍后继续。

任务库与 Mind 存储可以独立；任务侧通过同一事务写入结果与待交付事件，再由接线层转交。接收方按事件 ID 去重即可。

这借鉴的是持久执行系统对消息、等待和恢复的处理思路，不是要求安装 Temporal，也不是给每次操作增加第三套执行账本。([Temporal 文件檔案][8])

## 3. 立即可感知，不等于立即打扰用户

建议明确三个时间点：

```text
结果发生
    ↓
结果被持久记录
    ↓
Mind 有机会处理
    ↓
是否、何时向用户表达
```

前两步属于事实保存；第三步属于认知调度；第四步属于交互判断。

还必须区分两类表达：

**已经承诺的交付**不能因为 Mind 觉得“今天不值得说”就被默默吞掉。

**角色自己发现的内容**则可以先留着，等合适时机再提。

“主动联系自由”不能破坏“用户委托可靠”。

# 主题四：Skill——学习与泛化要发生，但不另造学习流水线

## 1. 保留当前轻量 Skill，补的是认知机会

现有 Skill 的读写机制适合作为基础。缺少的不是 `skill.merge()`，而是 Mind 是否能在合适的时候看到相关方法、关联真实经历，并有机会比较。

因此我建议提供两种观察：

**正常工作时**，按问题检索相关 Skill。

**闲暇反思时**，能看到近期确实学到或修改过哪些方法的简短目录。

不把全部 Skill 正文永久塞进上下文，也不要求每句话之前必须搜索 Skill。

这是“给模型看得到的材料”，不是替它判断哪些必须合并。

## 2. 泛化的对象应当是方法，不是标题相似度

例如：

```text
支付日志排查
上传日志排查
实验结果异常检查
```

模型可以发现共同结构：

> 寻找原始证据，区分观察与推断，定位影响范围，再提出可验证的下一步。

但这并不意味着领域细节可以全部删除。

我建议形成：

```text
通用方法
    +
仍有独立价值的场景变体
```

而不是为了减少条目数量，把所有方法压成“认真分析、注意细节”。

ExpeL 研究了从成功/失败比较中提炼跨任务经验；ACE 则明确指出，整体重写积累上下文可能造成细节丢失和性能下降。因此我会采用**局部修正、保留例外、允许抽象与具体方法并存**的方式。([arXiv][5])

## 3. “学会”必须看后续效果，不看保存动作

以下三种内容应当区分：

> 用户教过的方法。
> 这次执行中看起来有效的方法。
> 已在不同情况下复用过的方法。

第一种不必先执行才能保存；第二种不能自动升级成普遍规律；第三种也允许被新反例修正。

这些区别可以先写在正文和来源中，不必马上新增置信度、评分或自动晋升状态机。

对于自主整理，Mind 可以选择：

```text
读取相关方法
→ 比较证据与差异
→ 新建通用方法或修正旧方法
→ 在后续任务中检验
```

删除旧方法是另一项选择，不是泛化的必然后果。

## 4. 与外部 Skill 生态保持接口，但不强制迁移

Agent Skills 的公开规范采用 `SKILL.md` 和渐进加载，并允许附带脚本与参考资料。因此，“Skill 只能是自然语言、永远不能附代码”也不适合作为永久架构原则。([Agent Skills][12])

对 Lykoi，更准确的边界是：

> **Skill 描述做事方法；附带脚本是可用材料；真正执行仍走已有执行入口。**

当前没有必要为了对齐格式重做 P4。需要导入外部方法时，再加薄的适配即可。

# 主题五：并行任务——统一身份，不统一成一个阻塞队列

这是新架构必须认真处理的部分。

## 1. Mind 的一致性不靠“所有事情排队”

我建议采用：

> **认知计算可以并行，关键状态提交保持有序。**

后台思考、前台聊天和任务 Worker 可以使用各自的上下文快照。只有在更新同一个 Thought、用户偏好、任务要求或承诺时，才进行很短的版本检查与提交。

不能在等待 LLM、网页或 Pi 的时候持有整个 Mind 的锁。

Actor 系统对单线程状态处理与请求交错的区分，可以作为工程参考；Lykoi 要借的是状态所有权，而不是把长时间网络等待全部串行化。([Microsoft Learn][13])

## 2. 前台交互拥有独立的响应机会

后台同时存在五个任务，不应该占满全部模型请求额度，让用户一句“暂停刚才那个”也排在后面。

需要一个简单的资源调度：

**前台交互优先获得响应机会；后台任务和空闲思考在剩余额度内推进。**

这并不等于框架替模型决定哪些人生目标重要。

应区分：

| 决策                  | 归谁             |
| ------------------- | -------------- |
| 哪件事情更值得推进、是否改变目标    | Mind           |
| 当前空闲的执行槽给谁、如何避免长期饥饿 | 简单调度器          |
| 某个任务里面下一步怎么实现       | 当前任务的认知/Worker |

无需让模型为每一次线程调度开一次会。

## 3. 任务上下文必须隔离

每个 Task 有自己的材料、操作记录、工作目录和执行会话。

Mind 看到的首先是目标与摘要，只有需要理解具体结果时才读详细材料。这样 Task A 的几万行构建日志不会冲走用户刚表达的偏好，也不会污染 Task B 的上下文。

同样，用户修改某个任务时，影响的是该任务的新要求；不应使所有后台思考都因“全局版本变了”而被迫重跑。

## 4. 现实冲突不能只靠事后告诉模型

这里也需要修正此前的建议。

两个任务同时改同一个文件，不能等覆盖已经发生，再告诉 Mind“发生冲突”。

最小可行方式是：代码任务用独立工作树或工作目录；写回共享对象时检查原版本，或者对该对象串行提交。

**防止静默覆盖属于数据一致性，不属于过度防御。** 冲突出现以后，采用哪一份、如何合并、是否重新工作，再交给 Mind。

# 主题六：主动找用户——学习兴趣，也学习关系中的分寸

## 1. 对用户的理解应当是带证据的判断

我不建议把用户模型做成一排固定标签：

```text
Agent = 0.9
论文 = 0.8
GPU = 0.7
```

更适合的记录是：

> 最近关注持续认知与自主行动，目的是重新设计 Lykoi；特别在意方案是否轻量，而不是收集所有 Agent 新闻。

这条理解应该保留相关来源与时间范围，并区分用户明确说过的话和模型自己的推断。

PRELUDE/CIPHER 对“从修改中推断情境化自然语言偏好”的研究，与这里很接近。但它的模拟用户设定不能直接替代真实长期交互验证。([arXiv][6])

同时，**用户模型与角色自己的兴趣不能混为一谈**。

Lykoi 可以自己对某个问题感兴趣，不必每次都证明它能立刻为用户服务；但她自己喜欢的东西，也不能被写成“用户一定喜欢”。

## 2. 主动行为应有三种合法落点

当 Mind 发现一个可能相关的东西：

**现在告诉用户。** 内容真正相关、新颖，且适合此刻。

**留到下次自然交流。** 值得说，但不值得单独打扰。

**只影响自己的理解。** 没必要发消息，但值得记住或调整后续工作。

这比“发现相关内容 → 推送”多了重要的一层判断。

ProAct 的研究也区分主动交付、融入后续响应及静默吸收等使用方式；我会借这个行为划分，但不照搬其预测器、评分器和交付门控为三个新服务。([arXiv][10])

## 3. 反馈必须准确归因

同一句“不太喜欢”，可能在纠正内容、时间、格式，也可能在纠正她对用户的理解。

| 用户反馈            | 应该学到什么        | 不应学成什么       |
| --------------- | ------------- | ------------ |
| “这个方向很好，以后多告诉我” | 此类内容适合主动分享    | 所有相邻领域内容都值得推 |
| “这种小更新不用特意说”    | 提高该类内容的通知价值门槛 | 用户不再关心这个项目   |
| “太长了，先给结论”      | 调整表达方式        | 用户不喜欢这个主题    |
| “现在忙，晚上再说”      | 调整这次或此类联系时机   | 用户永久拒绝相关话题   |
| 没回复             | 目前没有明确反馈      | 用户讨厌、满意或关系变差 |

反思可以是：

> 我把“关注自主认知”泛化成了“喜欢所有 Agent 新闻”。用户纠正了这个范围。以后普通产品更新不主动推送，涉及持续思考与行动闭环的内容再考虑。

这是可以进入后续上下文的学习结果，不需要训练一个新的推荐模型。

但对于“不要再发”“取消”“这项信息是错的”这种明确反馈，不应等下一次深度反思才生效。**明确控制先落地，细致理解随后完成。**

## 4. 不以用户回复数量优化关系

主动性的目标应当是：

> 找得对、说得合适、被纠正后会变化。

而不是最大化打开率、依赖感或聊天时长。

Microsoft 的人机交互指南强调合适时机、可纠正、可控制与随时间适应，这些比“让角色更会黏人”更适合作为产品准则。([Microsoft][14])

因此，不能把用户没回复硬编码成角色焦虑，也不能为了表现“惦记”而制造催促与内疚。真实关系连续性应来自被记住、被理解和反馈有效。

# 主题七：真实体验——让系统状态与用户感受一致

## 1. 思考过程要可验证，但不必全部展示

用户可以选择看到很短的状态：

> “还在想上次那个问题。”
> “发现了一个可能推翻原结论的证据，正在确认。”

这些必须有对应的 Thought 或实际工作依据，不能由前端定时生成“她正在思考”的假动态。

用户最终更应该通过行为感受到连续性：

> 昨天没解决的问题，今天被新信息重新接起；
> 昨天纠正的偏好，今天已经改变了她的选择。

**一页写得很像人的日记，不足以证明 Mind 有效。**

## 2. 完成、结果与送达继续分开

你提供的 Telegram 测试说明，至少在被测环境中，延后跟进没有让用户获得可靠而清楚的闭环。但仅凭摘要，还不能确认是当前 Task Runtime、旧部署还是通道接线的问题。

后续应该追踪同一件事的：

```text
用户交代
→ 任务确实保存
→ 实际执行
→ 结果或失败原因
→ 发送尝试
→ 通道返回
→ 用户实际看到的内容
```

“进程结束”不能显示成“目标已完成”；“目标完成”不能显示成“用户已收到”。

投递失败时应重发已有结果，而不是重新做任务。通道返回发送成功，也不等于用户已经阅读。

## 3. Surface 要跟着主干一起做，不做另一套业务系统

最小 Surface 可以只有聊天、任务进展、成果入口，以及可选的思考摘要。

AIRI 的公开实现已在语音、VRM/Live2D 和多端表达上提供了可参考的方向；但其 README 中的身体能力，并不能替我们验证持续认知和学习闭环。

所以我的顺序是：

> **先让真实 Mind 状态有一个清楚的窗口；身体表现逐步增强，不让 Avatar 工程挡住核心体验，也不让漂亮表现掩盖断掉的闭环。**

---

## 四、这些功能如何保持轻量

七个主题不应对应七个新框架。

我建议保留下面这个工程边界：

| 部分      | 保留或新增的最小职责         | 明确不建设                            |
| ------- | ------------------ | -------------------------------- |
| Mind    | 事件入口、工作集、认知片段、状态提交 | Planner/Reviewer/Supervisor 常驻团队 |
| Thought | 可恢复的问题与进展          | 强制心理评分、情绪驱动状态机                   |
| Task    | 独立工作、等待、恢复、取消、成果   | 通用 DAG 平台、复杂分布式调度                |
| Skill   | 方法的发现、读取和局部更新      | Merger、排行榜、自动晋升引擎                |
| 用户理解    | 有来源、有情境、可修正的记录     | 单独的推荐系统和用户画像平台                   |
| Surface | 真实消息、状态与成果的呈现      | 第二套任务状态或人格管理                     |
| Cordis  | 插件装配、服务依赖、生命周期     | 决定角色该想什么                         |

### 对持久化，我收回“全部做成 Journal 投影”的倾向

统一时间线有价值，但**不代表所有状态都要做完整 Event Sourcing**。

Task 继续拥有自己的任务存储，Skill 继续使用文件，Memory 保留适用的存储实现。Mind 增加少量事件与工作状态即可；跨模块通过稳定引用连接。

不需要为了“像认知操作系统”再引入 Kafka、Redis、全局事件回放和一套投影管理器。

### 对防御性编程，继续采用事实边界

保留原子写入、必要的版本检查、真实错误、资源回收和不可逆操作记录。

删除或拒绝“无结果就编一个结果”“状态不好就不许思考”“失败两次就替模型认定不值得继续”“无人回复就推断关系恶化”等语义替代。

但也不走向另一个极端：

> **轻框架不是没有机制，而是每个机制都有明确的现实职责。**

---

## 五、我建议的开发流程

我不建议一次提交一个全新的“Lykoi 2.0”，也不建议只补几个触发器就宣告完成。

采用三个可直接体验的纵向批次，Surface 随每批一起推进。

### P5-A：让一个念头真正跨时间活下来

建立最小 Mind 工作集与持久事件入口，支持纯思考、保存进展、再次考虑、继续或放下。

Conversation 与 Wake 逐步成为不同输入和时延需求，而不是两个独立的状态编排中心。可以有不同上下文，不能各维护一套不相通的承诺与当前理解。

**验收：没有新任务、没有新工具调用，也能在重启后继续一个未解决问题，并利用后来出现的信息改变原判断。**

这一批最重要，因为它直接验证你强调的“想”，而不是再次证明 Agent 会执行工具。

### P5-B：让想法与并行工作形成闭环

接通自主/用户来源的通用任务创建、可靠结果回流，以及前台与后台的执行资源分离。

保留 Task、Pi、操作恢复等已验证机制；改变的是它们与 Mind 的关系，以及必要的并行调度。

把延后跟进问题纳入这里：先确认真实部署与故障路径，再修复已证实的断点，不根据错误名称猜原因。

**验收：Mind 自己提出一个研究目标，后台执行；期间用户正常聊天和修改另一件事；结果回来后 Mind 确实调整后续判断。**

### P5-C：让经历改变技能和主动交流

在同一 Mind 机制中增加近期方法变化、用户反馈等观察材料，使 Skill 凝练、用户理解修正和主动分享能够发生。

不新增 SkillMerger 或 ProactiveAgent。

**验收：她能从多个实际案例中形成可迁移方法；主动分享被用户纠正以后，下一次的内容、时机或表达出现正确变化。**

在迁移过程中，新旧认知入口可以短期用于对照，但同一正式实例不能有两套脑同时改写同一状态。新路径验收完成后退休旧路径，避免永久双轨。

## 六、怎样证明它真的满足七个主题

验收不能只问模型“你有没有记住”“你是不是成长了”。

| 主题       | 关键验收                | 必须看到的证据                    |
| -------- | ------------------- | -------------------------- |
| 持续思考     | 重启或隔一段时间后继续旧问题      | 旧进展被实际读取，新理解不是从零复述         |
| 想到行动     | 没有用户直接下任务时选择开展研究    | Thought 与真实 Task/操作之间有来源联系 |
| 结果回流     | Mind 忙碌时任务完成，稍后仍被处理 | 事件未丢、没有重复执行、判断受到结果影响       |
| Skill 成长 | 泛化方法用于未参与凝练的新案例     | 新成果正确，场景例外未被抹掉             |
| 并行工作     | 多任务等待/执行时仍能及时聊天和取消  | 上下文不串、迟到结果归属正确、共享文件不被覆盖    |
| 反馈学习     | 用户纠正兴趣范围、联系时间或表达方式  | 后续只改变相关维度，没有错误泛化           |
| 体验可靠     | 工作完成但发送失败           | 用户得到准确状态，重试只处理交付           |

LongMemEval 对跨会话、时间推理、信息更新和不确定时拒答的评测维度，可以用来设计记忆测试；ProEvent 对不必要行动及多线程语境的测试，可以补主动行为验收。但这些都要转化为 Lykoi 的实际场景，而不是直接以公开榜单代替产品验证。([arXiv][15])

我还建议做一个很小的对照实验：

**同一个模型、同一批工具、相近总预算，比较 P4 基线与新 Mind。**

再分别关闭 Thought 续接、反馈记忆或 Skill 复用，观察哪些效果确实来自新增机制。

重要指标不是“生成多少念头”，而是：

**有用的思考续接、实际任务完成、反馈后的行为修正、不必要的打扰、前台响应时延，以及总计算成本。**

总成本必须包含后台思考、Worker、反思和检索准备；不能只展示“下一次回答省了多少 token”，却不计之前已经消耗的计算。

---

## 最终决定

我不建议继续沿着：

> P4 完成 → 再加一个 Skill 功能 → 再加 Forge → 最后补体验

这条路线往前堆。

我建议正式转成：

> **先建立可恢复、能独立推进的思考过程；再让工作结果与用户反馈持续改变它。**

新的 Lykoi 不需要更多心理名词，也不需要一个包办所有事的巨大 Mind 类。它需要的是几条真正承重的关系：

**她在想什么，能够留下并继续。**
**她决定做什么，能够成为可靠工作。**
**现实返回什么，能够改变原来的理解。**
**用户怎样回应，能够改变后续相处方式。**

这四件事成立之后，Skill 泛化、主动分享、跨任务协作和身体表达都有自然的位置。

**所以我最终批准的方向是：重构认知主干，复用现有执行底座；以“持续思考与真实反馈”为中心，而不是以工具、任务或治理为中心。**
